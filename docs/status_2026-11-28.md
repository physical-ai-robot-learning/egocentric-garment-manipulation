# Status 2026-11-28: the first training on the new collection is running, and a faster inference path

Follows [status_2026-11-27.md](status_2026-11-27.md). No policy has a success rate, and nothing was run on the robot in
this period.

## 1. Questions

1. Is the training set of the new collection final, and is the first training on it running?
2. Can one inference on the robot computer be made fast enough for tighter re-planning, without changing its output?

## 2. Training data: 236 demonstrations

- The last take of 27 November (7 demonstrations) finished conversion; 2 of its demonstrations were kept after review.
  The training set is therefore **236** demonstrations (120 of 26 November, 116 of 27 November; 202,082 frames at
  0.5× speed and 20 Hz), not the 234 of status 11-27. 20 of them were recorded with the fixed camera at 1920×1080, the
  others at 848×480; the policy sees both at the same input size.
- Validation and test are unchanged: 15 / 15 demonstrations of 25 November, never trained on.

## 3. First training on the new data (running)

- The high-resolution wrist DiT (status 11-26, epoch-5 checkpoint) is being fine-tuned for 100 epochs on the 236
  demonstrations (198 updates per epoch, 19,800 in total), on eight rented RTX 5090 GPUs. It started on 27 November and
  had done 11,540 of the 19,800 updates (epoch 58) on the morning of 28 November.
- Compiling the model reduced the time per update from 5.0 to 4.0 s without changing the loss (within 0.03 %).
- The grasp-probability input (`PGRASP`) is off in this training, as planned; it had been on only in an evaluation
  setting, which was corrected.
- **No validation results yet.** The automatic per-checkpoint evaluation on the robot computer failed overnight and
  was rebuilt on 28 November; it now evaluates selected epochs while training runs.

## 4. Inference on the robot computer

- **A deploy mismatch fixed.** The robot-side inference passed the high-resolution wrist images of the previous and the
  current step to the model, while training used only the current one. This probably applied to every
  high-resolution checkpoint since 23 November, including the uncounted robot tests of 24–26 November (status 11-26).
- **Faster inference.** One inference with 5 integration steps took 1,455 ms in the previous Python deploy and 844 ms
  after the fix above. The image encoders and the DiT were exported to Core ML (fp16, Mac GPU) and are driven by a small
  Rust program: 101 ms (encoders 76 ms, then 5 DiT steps). With the same noise, its predicted positions differ from
  PyTorch fp32 by 0.3–0.6 mm on 3 frames. The speed comes from running the models on Core ML, not from the language.
- It is not yet connected to the robot deploy.

## 5. What is not shown

- No validation or test number for the running training.
- No robot runs; the faster inference has not driven the robot.
- The Core ML agreement is checked on 3 frames only.
